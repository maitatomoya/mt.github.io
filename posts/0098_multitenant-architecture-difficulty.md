## はじめに

業務SaaSの設計を考えていると、必ずぶつかるのが「マルチテナント」という壁である。

シングルテナントのアプリケーションなら、`WHERE`句を1つ書き忘れてもそれはただのバグで済む。表示が変になる、件数が合わない、その程度である。ところがマルチテナントでは、同じミスが**他社のデータが見える情報漏えい事故**になる。バグの重さが根本的に違う世界なのだ。

本記事では、マルチテナントアーキテクチャの基本を整理した上で、実際に設計してみると痛感する「4つの難しさ」を、コード例を交えて解説する。読み終わったあとに、AWSやMicrosoftが公開しているSaaS設計ガイド（記事末尾にリンクを掲載）を読む足がかりになることを目指す。

## マルチテナントとは

**テナント（tenant）**とは「借り手」という意味で、SaaSにおいては契約している顧客企業1社を指す。マルチテナントとは、**1つのシステムを複数の顧客企業が共同利用する構成**のことである。

```
シングルテナント                マルチテナント
（顧客ごとに環境を用意）        （1つの環境を全顧客で共有）

A社 → [アプリA] → [DB-A]       A社 ┐
B社 → [アプリB] → [DB-B]       B社 ┼→ [アプリ] → [DB]
C社 → [アプリC] → [DB-C]       C社 ┘
```

SaaSがマルチテナントを選ぶ理由はコストである。顧客が1,000社いても運用するシステムは1つ。サーバー費用も、デプロイも、監視も1回で済む。月額数千円〜数万円で提供する業務SaaSは、マルチテナントでなければ商売が成立しない。

### 実装方式は大きく3つ

| 方式 | 概要 | 分離の強さ | コスト・運用 |
|:---|:---|:---|:---|
| 共有スキーマ | 全テナントが同じテーブルを共有し、各行の`tenant_id`列で区別する | 弱い（アプリの実装に依存） | 最も安い。マイグレーションは1回 |
| スキーマ分離 | 1つのDB内にテナントごとのスキーマ（テーブル群を束ねる名前空間。フォルダのようなもの）を作る | 中 | スキーマ数の管理が必要 |
| データベース分離 | テナントごとに物理的にDBを分ける | 強い | 最も高い。DB数×運用 |

多くのSaaSは共有スキーマ方式から始まる。安くて速いからだ。そして本記事で扱う「難しさ」の多くは、この共有スキーマ方式を選んだときに顕在化する。

## 難しさ1：分離が「構造」ではなく「規約」になってしまう

共有スキーマ方式の本質的な弱点はこれである。

**データの分離を守っているのは、データベースではなく、アプリケーションコードの全行に書かれた`WHERE tenant_id = ?`である。**

つまり分離は「仕組み」ではなく「開発者が守り続ける規約」になる。そして規約は、いつか誰かが破る。

### やりがちな失敗例

```typescript
// 悪い例：URLのidだけで案件を取得している
app.get("/api/projects/:id", async (c) => {
  const project = await db
    .prepare("SELECT * FROM projects WHERE id = ?")
    .bind(c.req.param("id"))
    .first();
  return c.json(project);
});
```

このコードは自分のテナントのデータを見る分には正しく動く。テストも通る。しかし攻撃者が他社の案件IDをURLに直接指定すると、**他社の案件がそのまま返ってくる**。これはIDOR（Insecure Direct Object Reference：認可されていないオブジェクトへの直接参照）と呼ばれる脆弱性で、マルチテナントSaaSで最も典型的な事故パターンである。

```typescript
// 良い例：常にtenant_idとの複合条件で取得する
app.get("/api/projects/:id", async (c) => {
  const tenantId = c.get("tenantId"); // 認証ミドルウェアがセッションから解決した値
  const project = await db
    .prepare("SELECT * FROM projects WHERE tenant_id = ? AND id = ?")
    .bind(tenantId, c.req.param("id"))
    .first();
  if (!project) return c.json({ error: "not found" }, 404);
  return c.json(project);
});
```

ポイントは、`tenant_id`を**リクエストパラメータから絶対に受け取らない**ことである。必ずサーバー側でセッションから解決する。クライアントが送ってきた`tenant_id`を信用した瞬間、分離は崩壊する。

### 漏れる経路はWHERE句だけではない

厄介なのは、分離が破れる場所がSQLだけではないことだ。設計時にチェックすべき経路を挙げる。

| 経路 | 事故の例 |
|:---|:---|
| JOIN・集計クエリ | 集計だけtenant_id条件を忘れ、全社合算の数字が表示される |
| キャッシュ | キャッシュキーにtenant_idを含め忘れ、A社向けのキャッシュがB社に配信される |
| 検索インデックス | 全文検索・ベクトル検索のインデックスが全テナント共有で、検索結果に他社文書が混ざる |
| ファイルストレージ | オブジェクトストレージのキー設計にテナント区分がなく、URL推測で他社ファイルに到達できる |
| ログ・エラーメッセージ | 例外メッセージに他テナントのデータが含まれ、エラー画面や監視ツールに漏れる |
| バックグラウンドジョブ | 非同期処理がリクエストコンテキストを失い、テナント横断でデータを処理してしまう |

「データベース以外にも分離すべき面がある」という視点は、AIを組み込んだSaaSではさらに重要になる。たとえばRAG（検索拡張生成。生成AIに社内文書などを検索させて、その内容を根拠に回答させる技術）を実装するなら、ベクトルインデックスもテナントごとの名前空間に分けなければ、チャットの回答に他社のドキュメントが引用される事故が起きる。

もう1つ見落とされがちなのが、自社のサポート・運用メンバーが使う管理画面、いわゆる全テナントを横断して閲覧できるグローバルビューである。運用上必ず必要になる一方で、これはテナント分離の「正規の例外」であり、この管理者権限が乗っ取られると被害は全テナントに及ぶ。横断アクセスできる経路は最小限に絞り、多要素認証と監査ログで通常のユーザー権限とは別枠で守る設計を、最初から分けて考えておきたい。

### 対策1：規約を構造に変える

規約は破られる前提で、「守らないとコードが書けない」構造を作るのが定石である。

1つのパターンは、ハンドラに生のDB接続を渡さず、**テナントIDを閉じ込めたラッパーだけを渡す**方法だ。

```typescript
// tenant_idを閉じ込めたDBラッパー
// ハンドラからは生のSQLを書けず、必ずテナントスコープ付きのメソッドを通る
function scopedDb(db: D1Database, tenantId: string) {
  return {
    async findProject(id: string) {
      return db
        .prepare("SELECT * FROM projects WHERE tenant_id = ? AND id = ?")
        .bind(tenantId, id)
        .first();
    },
    async listProjects() {
      return db
        .prepare("SELECT * FROM projects WHERE tenant_id = ? ORDER BY updated_at DESC")
        .bind(tenantId)
        .all();
    },
    // 以下、全クエリがtenant_idを強制される
  };
}

// 認証ミドルウェアでscopedDbを生成し、ハンドラにはこれだけを渡す
app.use("/api/*", async (c, next) => {
  const session = await resolveSession(c);
  c.set("db", scopedDb(c.env.DB, session.tenantId));
  await next();
});
```

PostgreSQLを使っているなら、**RLS（Row Level Security：行レベルセキュリティ）**でデータベース側に分離を強制させる選択肢もある。

```sql
-- テナント分離ポリシー：接続セッションに設定されたテナントIDの行しか見えなくする
ALTER TABLE projects ENABLE ROW LEVEL SECURITY;
-- テーブル所有者としての接続にもポリシーを強制する（忘れると本番でRLSが素通りする）
ALTER TABLE projects FORCE ROW LEVEL SECURITY;

CREATE POLICY tenant_isolation ON projects
  USING (tenant_id = current_setting('app.tenant_id', true)::uuid);
```

2箇所、実務でハマりやすい注意点がある。まず`FORCE ROW LEVEL SECURITY`を付けないと、テーブル所有者として接続しているアプリケーションにはポリシーが適用されず、「開発環境では効いていたのに本番では素通りだった」という事故が起きる。また`current_setting`の第2引数に`true`を渡しておくと、パラメータ未設定時にエラーで落ちる代わりにNULLが返る（NULLとの比較は偽になるので、行は1件も返らない安全側に倒れる）。

RLSを有効にすると、アプリケーションがWHERE句を忘れても、DBが他テナントの行を返さない。多層防御の要になる機能だが、SQLiteベースのDB（Cloudflare D1など）にはこの機構がないため、その場合はアプリ層のラッパーパターンで守るしかない。**選んだDBにRLS相当の機構があるかどうかは、マルチテナントSaaSの技術選定における重要な観点**である。

### 対策2：「越境テスト」を書く

分離バグの怖さは、**正常系のテストでは絶対に見つからない**ことにある。自分のテナントのデータは正しく見えるからだ。そこで、意図的に他テナントのデータへアクセスを試みるテストを書く。

```typescript
// 越境テスト：テナントAのユーザーがテナントBの案件を取得できないこと
test("他テナントの案件IDを指定すると404が返る", async () => {
  const projectB = await createProject(tenantB, "B社の極秘案件");

  const res = await request("/api/projects/" + projectB.id, {
    headers: { Cookie: sessionCookieOf(tenantAUser) },
  });

  expect(res.status).toBe(404); // 403ではなく404を返し、存在自体を秘匿する
});
```

ここで403（Forbidden）ではなく404を返しているのは意図的である。403を返すと「そのIDのデータは存在する」という情報自体が攻撃者に渡ってしまう。他テナントのリソースは**存在ごと隠す**のがマルチテナントの定石だ。

このテストを全リソース（案件・顧客・勤怠・ファイル・検索…）に対して機械的に用意しておくと、後から入った開発者がWHERE句を忘れてもCIで検知できる。マルチテナントSaaSにおいて、越境テストは単体テストより優先度が高いと言ってよい。

## 難しさ2：noisy neighbor — 隣のテナントがうるさい問題

**noisy neighbor（うるさい隣人）**とは、1つのテナントの過剰な利用が、同居する他のテナント全員の性能を劣化させる問題である。

- 1社が数十万行のデータを取り込み、その集計クエリがDBを占有する
- 1社がAPIを高頻度で叩き、他社のリクエストが待たされる
- 1社の全文検索インデックスが肥大化し、全体の検索が遅くなる

共有こそがマルチテナントのコストメリットの源泉なので、この問題は構造的に避けられない。対策は段階的に打つ。

1. **レート制限**：テナント単位・ユーザー単位でAPI呼び出しを制限する
2. **クォータ**：プランごとにデータ量・利用量の上限を設ける
3. **重い処理の非同期化**：集計やインポートはキューに逃がし、オンライン処理と分離する
4. **大口テナントの物理分離**：どうしても収まらない顧客は専用リソースに移す

見落とされがちだが、これらすべての前提として「**どのテナントがどれだけ使ったか**」を計測する仕組みが要る。このメータリング基盤は従量課金の計算にもそのまま使うため、性能対策と課金設計はセットで考えると設計が二度手間にならない。

## 難しさ3：運用の単位が「×テナント数」になる

実際にサービスを運用し始めると、一番効いてくるのはこの軸である。代表例をいくつか挙げる。

### 「1社だけ昨日に戻したい」問題

共有スキーマでは、バックアップは全テナント一体である。ある1社が誤操作でデータを大量削除してしまい「昨日の状態に戻してほしい」と言われたとき、DB全体をリストアすると**他の999社まで昨日に巻き戻ってしまう**。実際には、特定時点のバックアップを別環境に復元し、該当テナントの行だけを抽出して書き戻すという手術になる。この手順を事前に設計・訓練していないと、障害対応の現場で詰む。

### マイグレーション事故が全社に波及する

スキーマ変更（マイグレーション。テーブル定義の追加・変更など、データベースの構造を更新する作業）は1回で全テナントに適用される。便利である反面、失敗も全社規模になる。特に怖いのが、データが肥大化した共有テーブルへのDDL適用だ。カラム追加やインデックス作成のロックが長引けば、全テナントが同時にサービス停止する。1社の巨大テナントのデータ量が、全社のメンテナンス性を人質に取る構図である。逆にデータベース分離方式を選ぶと、今度は数百〜数千のDBに同じマイグレーションを順番に適用する仕組みが必要になり、「適用途中で失敗したらDBごとにスキーマバージョンがずれる」という別の地獄が待っている。

### 退会時のデータ削除義務

顧客が解約したら、そのテナントのデータを完全に削除する必要がある。個人情報保護法やGDPR（EU一般データ保護規則）は消去義務を定めており、「共有テーブルの中から1社分だけを、バックアップやログも含めて確実に消す」のは、言うほど簡単ではない。テナント単位のエクスポート（データ持ち出し）要求への対応も同様である。

こうして見ると、共有スキーマとデータベース分離のどちらを選んでも固有のつらさがあることが分かる。**どちらが正解かではなく、事業フェーズによってどちらのつらさを引き受けるかという判断問題**なのである。

| 観点 | 共有スキーマ | データベース分離 |
|:---|:---|:---|
| 初期コスト・速度 | ◎ 安く速い | △ 環境構築が重い |
| 分離事故のリスク | △ アプリ実装に依存 | ◎ 構造的に守られる |
| 1社だけのリストア | △ 手術が必要 | ◎ そのDBを戻すだけ |
| マイグレーション | ◎ 1回で全社 | △ 全DBへの適用管理 |
| 大口・監査要求への対応 | △ 難しい | ◎ 専有・リージョン指定に応えやすい |

現実解としてよく採られるのは、**共有スキーマで始めて、エンタープライズ顧客や監査要件が出てきた段階で大口だけを分離するハイブリッド構成**である。ただしそのためには「テナントを後から引っ越せる」設計（テナントIDが全テーブルに貫通していること、データ抽出ツール）を最初から仕込んでおく必要がある。

## 難しさ4：テナントごとの差異がスキーマを侵食する

業務SaaSの顧客は1社ごとに業務ルールが違う。勤怠の締め日、承認フローの段数、評価制度の項目。これらの差異をどう吸収するかで、2つの悪い未来がありうる。

- **設定で吸収しすぎる**：設定項目が数百に膨らみ、設定の組み合わせテストが爆発する。「設定地獄」と呼ばれる状態
- **個社対応でコードを分岐させる**：`if (tenantId === "...")`が増殖し、共有スキーマの意味が崩壊する。実質シングルテナントの寄せ集めになる

### 「A社はこの機能が欲しい」にどう応えるか

では、テナントごとに欲しい機能が違うとき、クライアントごとに機能追加していくしかないのだろうか。マルチテナントでそれはタブーなのだろうか。

答えは「**個社向けの機能提供自体はタブーではない。タブーなのは、特定テナントを名指しするコード分岐とテナント別フォーク**」である。正攻法は次の順で考える。

**1. 機能フラグ（feature flag）とプラン設計で吸収する。** コードは「どのテナントか」ではなく「どの機能が有効か」で分岐させる。

```typescript
// 悪い例：テナントの「名前」で分岐する。増殖すると管理不能になる
if (tenantId === "tenant-a") {
  await runAdvancedApprovalFlow(request);
}

// 良い例：テナントに紐づく「機能の有効状態」で分岐する
if (await features.isEnabled(tenantId, "advanced-approval-flow")) {
  await runAdvancedApprovalFlow(request);
}
```

機能フラグは個社ごとにバラバラにONにするのではなく、「スタンダードプランはここまで、エンタープライズプランはここまで」と**プラン（エディション）に束ねて売る**のが基本である。A社の要望で作った機能は、A社専用ではなく上位プランの標準機能として一般化する。こうすれば開発は1本のコードベースのまま、要望には応えられる。

**2. 枠組みを標準化し、中身を設定・データにする。** 「承認フローの段数」「カスタム項目」のような差異は、機能ではなく設定として持たせる。この方向の極致がSalesforceのメタデータ駆動アーキテクチャで、カスタマイズをコードではなくデータとして表現することで、1つの基盤の上に無数の個社差を載せている。

**3. それでも吸収できない個社固有ロジックは、プラットフォームの外に出す。** APIとWebhookを公開し、顧客側・パートナー側で作ってもらう。本体のリリースサイクルを個社要望から切り離すための出口である。

**4. 最後の手段が、エンタープライズ専有（実質シングルテナント）＋特別価格。** どうしても飲みたい大口の個社要望は、共有環境から隔離した専有環境で、その運用コストに見合う価格を付けて引き受ける。

要望が来たときの判断基準は1つで、「**この要望を一般化して、他のテナントにも価値がある標準機能にできるか**」である。できるならプランに載せてロードマップへ、できないなら3か4へ回すか、断る。

これは技術だけでは解けない。「どこまでを標準機能として吸収し、どこからは対応しない（顧客を選ぶ）か」というプロダクト戦略の判断であり、マルチテナントSaaSの設計とは、実はビジネスの標準化戦略そのものなのである。

## まとめ — 難しさの正体は「破れる面の多さ×被害の単位×時間変化」

マルチテナントアーキテクチャの難しさを一枚にまとめると、こうなる。

1. **分離**：守るべき面が多く（SQL・キャッシュ・検索・ファイル・ログ・ジョブ）、破れたときの被害が「バグ」ではなく「全顧客規模の情報漏えい」になる。規約ではなく構造とテストで守る
2. **性能**：noisy neighborは構造的に避けられない。テナント単位の計測を早めに仕込む
3. **運用**：バックアップ・マイグレーション・削除義務が「×テナント数」で効いてくる。1社だけ戻せるかを設計段階で考える
4. **差異**：テナントごとのカスタマイズ要求は、技術ではなくプロダクト戦略で線を引く

そして重要なのは、これらの正解が**事業の成長とともに変わる**ことだ。10社のときの最適解（共有スキーマで速く作る）と、1,000社のときの最適解（大口の物理分離・メータリング・移行ツール）は違う。最初から完璧な分離機構を作るのではなく、「分離を構造とテストで担保する仕組み」「テナント単位の計測」「方式を切り替えるトリガーの定義」の3つを先に置いておくのが、実務的な落としどころだと考えている。
