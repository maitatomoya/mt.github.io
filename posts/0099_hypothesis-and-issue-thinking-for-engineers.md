## はじめに

障害調査でログを最初から最後まで読み切ってから考え始める。「ダッシュボードを作ってほしい」と言われて、そのままダッシュボードを作る。技術選定の比較表を6列作ったら、誰も読んでくれない。

エンジニアとして数年働くと、こうした場面に必ず出会う。手は動いているのに成果が出ない、あるいは成果は出たのに「そこじゃない」と言われる。原因の多くは技術力ではなく、**何を解くか**と**どう解くか**の順番と決め方にある。

この2つをそれぞれ1冊で扱ったのが、内田和成氏（元ボストンコンサルティンググループ（BCG）日本代表）の『論点思考』と『仮説思考』である。コンサルタント向けの本だと思われがちだが、中身はデバッグや設計、チーム運営にそのまま使える。

本記事では2冊の章構成を地図として示したうえで要点をエンジニアの仕事に翻訳し、2冊をエンジニアの視点で扱ったSE猫氏の動画にも触れる。最後に筆者が実践ルールとして採用している「**ものごとを整理するときは軸を2つまでにする**」を添える。読み終えたあとに原著が読みやすくなることを目標にしている。

対象読者は、実務経験0年から3年の初心者エンジニアと、これからチームリーダーになるエンジニアである。前者には「調べる前に考える」習慣を、後者にはメンバーへの問いかけの型を持ち帰ってもらいたい。

## 先に用語を揃える

2冊を読むうえで混同しやすい言葉を先に整理する。

| 用語 | 意味 | エンジニアの例 |
|:---|:---|:---|
| 問題 | 目に見える現象、困りごと | 「CIが遅い」「問い合わせが増えた」 |
| 論点 | その中で**解くべきと決めた問い** | 「CIの待ち時間がレビューのボトルネックになっているか」 |
| 仮説 | まだ証明されていないが、最も答えに近いと思われる**仮の答え** | 「E2Eテストの直列実行が待ち時間の大半を占めている」 |
| 検証 | 仮説が正しいかを確かめる行為 | CIのステージ別所要時間を1週間分集計する |
| 網羅思考 | 情報を集めきってから答えを出そうとする進め方 | 全ステージのログを全期間分読んでから考える |
| 仮説思考 | 限られた情報で仮の答えを置き、検証しながら進める進め方 | 直列実行が原因と当てて、そのステージだけ先に測る |

「問題」と「論点」は特に混ざりやすい。問題は向こうからやってくるが、論点は自分で決めるものである。

本文の例で使う技術用語も先に補足しておく。

| 用語 | 意味 |
|:---|:---|
| N+1クエリ | 一覧を1回のクエリで取得したあと、行ごとに追加のクエリを発行してしまう典型的な性能問題。件数に比例して遅くなる |
| p95 | 全リクエストの応答時間を速い順に並べたときの95%地点の値。平均では見えない「遅い側の体感」を表す指標 |
| EXPLAIN | データベースがそのクエリをどう実行するか（実行計画）を表示するSQLコマンド。遅いクエリの原因調査に使う |

## 2冊の位置づけ

2冊は問題解決の上流と下流を分担している。

```
依頼・現象
   │
   ▼
[論点思考]  何を解くべきか決める        ← 上流：問いを選ぶ
   │
   ▼
[仮説思考]  たぶん答えはこれだと置く    ← 下流：答えに向かう
   │
   ▼
 検証 → 仮説の修正 → 検証 → ...
   │
   ▼
提案・実装
```

| 観点 | 論点思考（2010年） | 仮説思考（2006年） |
|:---|:---|:---|
| 答える問い | 何を解くべきか | どう解くか |
| 失敗の形 | 間違った問題を完璧に解く | 情報集めに溺れて遅くなる |
| キーワード | 筋の良い論点、依頼者の真意、論点の階層 | 空パッケージ、クイック＆ダーティ、仮説の進化 |
| リーダーにとっての意味 | メンバーに渡す問いを決める | メンバーが動ける仮の答えを示す |

出版は『仮説思考』が先だが、仕事の流れとしては論点思考が先に来る。本記事もその順で説明する。

なお、同じテーマを1冊で扱った本として安宅和人氏の『イシューからはじめよ』がある。解く価値のある問い（イシュー）を見極めずに大量の作業で押し切ろうとする進め方を「犬の道」と呼んで避けるよう説いており、本記事でいう網羅思考への警告と重なる。2冊を読んだあとの3冊目として相性がよい。

## 論点思考：解くべき問題を決める

### 本書の全体像：6章の地図

『論点思考』は6章構成で、前半で「論点とは何か」、中盤で「論点をどう絞り、確定するか」、後半で「ケースと鍛え方」を扱う。エンジニアが読むときの着眼点を添えて一覧にする。

| 章 | 主題 | エンジニアの読みどころ |
|:---|:---|:---|
| 第1章 あなたは正しい問いを解いているか | すべては問題設定に始まる。問題解決プロセスにおける論点の役割 | 「言われた通り作ったのに喜ばれない」の正体がここにある |
| 第2章 論点候補を拾いだす | 論点と現象を見極める。論点は動く | 障害報告や要望の「現象」から論点候補を切り出す練習 |
| 第3章 当たり・筋の善し悪しで絞り込む | 当たりをつける。筋の善し悪しを見極める | 技術的に面白い論点と、効く論点は別だと知る |
| 第4章 全体像を確認し、論点を確定する | プロービング、依頼主の真意、引き出しの参照、論点の構造化 | 上司や顧客との論点のすり合わせ方。設計レビューの前段で使う |
| 第5章 ケースで論点思考の流れをつかむ | 「原料費が上がっている。コストの問題を解決してほしい」という指示への対応 | 「クラウド費用が上がっている。何とかして」に置き換えて読める |
| 第6章 論点思考力を高めるために | 問題意識をもつ、視点を変える、複数の論点を考える、引き出しを増やす。論点と仮説の関係 | 日々の業務を訓練に変える方法。仮説思考への橋渡し |

以下では、この地図の中から実務で特に効く部分を順に取り上げる。

### 問題と論点は違う

『論点思考』の中心にあるのは、**間違った問題を解いても価値はゼロ**という立場である。正しい答えを出す能力より先に、正しい問いを立てる能力が問われる。

「CIが遅い」という問題を例にする。ここから立てられる論点の候補は1つではない。

- CIの実行時間そのものを短くすべきか
- CIの待ち時間がレビューのボトルネックになっているのか
- そもそもテストの粒度や配置に問題があるのか
- 遅いこと自体は許容でき、通知の仕組みが悪いだけなのか

どれを解くかで、やることも成果も変わる。実行時間を半分にしても、実際のボトルネックがレビュー待ちなら誰も楽にならない。

### 論点を決める4ステップ

本書は論点設定の手順を4段階で整理している。

| ステップ | やること | エンジニアの例 |
|:---|:---|:---|
| 1. 候補を拾い出す | 考えられる論点を幅広く書き出す | 上の4候補のように列挙する |
| 2. 絞り込む | 筋の良さで候補を減らす | 「解けるか、効果があるか、実行できるか」で選ぶ |
| 3. 確定する | 依頼者とすり合わせて1つに決める | 「レビュー待ち時間を短くする」で合意する |
| 4. 全体像で確認する | 上位の論点や隣の論点との関係を見直す | 「開発リードタイム短縮」の中でどこを担うか確認する |

### 筋の良い論点の3条件

ステップ2の「絞り込む」で使う基準は3つである。

| 条件 | 問い | 満たさない例 |
|:---|:---|:---|
| 解けるか | 自分たちの手で答えが出せるか | 「クラウド事業者側の障害をなくすには」 |
| 効果が大きいか | 解けたときにどれだけ状況が変わるか | 「月1回しか動かないバッチを3秒速くするには」 |
| 実行できるか | 出した答えを実際に実行に移せるか | 「全サービスを来月までに書き換えるには」 |

3つとも満たす論点を、本書は「筋の良い論点」と呼ぶ。逆に、解けない、効いても小さい、実行に移せない論点は「筋が悪い」。技術的に面白いかどうかは基準に入っていない点に注意したい。

### 依頼者の真意を探る

上司や顧客が口にする言葉は、たいてい論点そのものではなく、症状か思いついた解決策である。

たとえば上司から「障害のダッシュボードを作ってほしい」と言われたとする。ダッシュボードは解決策の1つに過ぎない。「なぜ欲しいのか」を辿ると、「障害が起きたときの一次報告が遅く、経営層への説明に困っている」という背景が出てくる。すると本当の論点は「障害の検知から一次報告までの時間を短くするには」であり、答えはダッシュボードかもしれないし、アラートの通知先変更かもしれないし、報告テンプレートかもしれない。

真意に近づく質問をいくつか持っておくと便利である。

- 「それができると、何が変わりますか」
- 「今いちばん困っている瞬間はいつですか」
- 「もしやらなかったら、何が起きますか」

本書が勧めるもう1つの方法は、**仮の論点を提示して反応を見る**ことである。本書ではこれを「プロービング（探針）」と呼ぶ。「レビュー待ちがボトルネックだと思うのですが、合っていますか」と投げると、相手は「いや、それより夜間バッチの失敗が痛い」のように、言語化していなかった本音を返してくれる。

### 論点には階層がある

論点は1つの平面に並んでいるのではなく、上位と下位の階層になっている。

```
大論点：開発のリードタイムを短くする
 ├─ 中論点：レビュー待ち時間を短くする
 │    ├─ 小論点：CIのどのステージが待ち時間の大半を占めているか
 │    └─ 小論点：レビュー着手までの待ちはどこで発生しているか
 └─ 中論点：リリース作業の手戻りを減らす
      └─ 小論点：手戻りはどの工程で最も多く発生しているか
```

自分が担当しているのが小論点なら、それが上のどの論点に効いているのかを説明できる必要がある。リーダーになると、大論点をメンバーが動ける小論点まで分けて渡すことが仕事になる。

### 論点は動く

同じ現象でも、論点は人によって、時間によって、環境によって変わる。半年前に決めた論点が今も最重要とは限らない。スプリントの振り返りや四半期の節目で「今の論点はまだこれでよいか」を問い直す習慣が、本書の「論点は動く」という指摘の実務的な受け止め方である。

### ケースで流れをつかむ：本書第5章の翻訳

本書の第5章は「原料費が上がっている。コストの問題を解決してほしい」と上司に言われた場面を題材に、論点思考の流れを通しで見せる。エンジニアなら「クラウド費用が上がっている。何とかして」に置き換えると、そのまま追体験できる。

| 流れ | 本書のケース（原料費） | エンジニアへの置き換え（クラウド費用） |
|:---|:---|:---|
| 現象を受け取る | 原料費が上がっている | 先月の請求額が前月比で大きく増えた |
| 論点候補を拾う | 単価の問題か、使用量の問題か、そもそも原料費が論点か | 単価改定か、利用量の増加か、無駄なリソースか、売上増に伴う自然増か |
| 当たりをつける | 効きそうな候補に仮の優先順位をつける | 請求明細をサービス別に見て、増分の大半を占める1つに当たりをつける |
| 依頼主の真意を探る | 上司が本当に困っているのは利益率か、資金繰りか | 「何とかして」の裏が利益率なのか、予算超過の説明責任なのかを聞く |
| 論点を確定する | 解くべき問いを1つに決め、上司とすり合わせる | 「売上あたりのインフラ原価率を下げるには」のように1文で合意する |

「コストを下げる」と「原価率を下げる」では打ち手が変わる。前者なら削減が答えになり、後者なら売上増に見合う設計も答えになる。論点の1文が変わると、解の空間が変わる。

### 論点思考力を高める：本書第6章より

本書の最終章は、論点思考を日常で鍛える方法を挙げている。エンジニアの実践に翻訳する。

| 本書の指摘 | エンジニアの実践 |
|:---|:---|
| 問題意識をもって仕事をする | 割り当てられたタスクごとに「これは何の論点に効くのか」を1行書く |
| 視点を変える | 開発者の立場だけでなく、運用担当・利用者・経営者の立場から同じ現象を見る |
| 複数の論点を考える | 1つの現象に対して最低3つの論点候補を出してから選ぶ |
| 引き出しを増やす | 過去の障害・設計判断・他社事例をメモとして蓄積し、論点候補を出すときに参照する |

本書でいう「引き出し」とは、過去の経験や知識のストックである。論点候補は無から出てくるのではなく、引き出しから引き出される。障害の振り返り（ポストモーテム）や設計判断の記録を残す習慣は、そのまま論点思考の訓練になる。

## 仮説思考：仮の答えから動く

### 本書の全体像：7章の地図

『仮説思考』は序章と終章を含む7章構成で、「なぜ仮説か」「仮説をどう使うか」「どう立て、どう検証するか」「どう鍛えるか」の順に進む。

| 章 | 主題 | エンジニアの読みどころ |
|:---|:---|:---|
| 序章 仮説思考とは何か | 仮説の定義。情報を集めてから考える網羅思考との対比 | 「調べてから考える」癖がなぜ遅いのかの説明 |
| 第1章 まず、仮説ありき | 情報が多いほど判断は遅れる。少ない情報で全体のストーリーを描く | 障害対応や見積もりで最初の1時間をどう使うか |
| 第2章 仮説を使う | 問題発見の仮説と問題解決の仮説。仮説の進化。空パッケージ | 設計ドキュメントやPull Requestの説明文を先に書く根拠 |
| 第3章 仮説を立てる | 反対側から見る、両極端に振る、ゼロベースで考える。分析結果・インタビュー・ディスカッションから立てる。良い仮説の条件 | 「仮説が思いつかない」ときの視点の動かし方。机上で考えすぎず、断片的な情報から立てるコツ |
| 第4章 仮説を検証する | 実験、ディスカッション、分析。クイック＆ダーティ | ログのサンプル確認や1件だけのEXPLAINが正当化される理由 |
| 第5章 仮説思考力を高める | 「So What?」を繰り返す。日常の訓練。失敗を恐れない | デバッグ以外の場面で仮説思考を習慣にする方法 |
| 終章 本書のまとめ | 全体の要約 | 読み返すときの索引として使える |

以下では、この地図の中から実務で特に効く部分を順に取り上げる。

### 仮説とは何か

『仮説思考』での仮説の定義は「まだ証明されていないが、最も答えに近いと思われる答え」である。当てずっぽうではなく、手元の情報から導いた**仮の結論**を指す。

本書が対置するのは網羅思考である。情報を集めれば集めるほど正しい判断ができる、という直感に反して、実務では情報が増えるほど意思決定は遅くなり、判断はむしろ鈍る。時間も情報も常に足りない前提で、それでも前に進む技術が仮説思考である。

仮説は外れてよい。外れた仮説を1つ棄却できたなら答えの候補が1つ減ったのだから、それは失敗ではなく前進である。初心者ほど「間違った仮説を立ててはいけない」と考えて情報集めに戻ってしまうが、本書の立場はその逆で、粗い仮説を早く出して早く外すことを勧めている。

```
網羅思考                          仮説思考

情報収集 ─────────────→ 分析 → 結論    仮説 → 検証 → 修正 → 検証 → 結論
（集めきるまで答えが出ない）           （最初から仮の答えがある）

時間 ━━━━━━━━━━━━━━━━━━━━━━━▶   時間 ━━━━━━━━━▶
```

### なぜ先に答えを置くのか

本書は仮説を先に置くことの利点を3つ挙げている。

1. **速くなる**。調べる範囲が「仮説を確かめるのに必要な情報」に限定される
2. **精度が上がる**。検証で外れた仮説を修正するたびに、答えが進化する
3. **全体像が早く見える**。仮の答えがあるので、最終アウトプットの形を最初から描ける

エンジニアにとって身近なのは1番目である。「原因は不明。ログを全部見ます」と「原因はおそらくコネクションプールの枯渇。まず接続数の推移を見ます」では、最初の1時間の使い方がまったく違う。

### 2種類の仮説

仮説には2種類あると本書は整理する。

| 種類 | 問い | デバッグでの例 |
|:---|:---|:---|
| 問題発見の仮説 | 何が問題なのか | 「遅いのはDBではなく外部API呼び出しの待ちではないか」 |
| 問題解決の仮説 | どうすれば解決するのか | 「外部API呼び出しを非同期化すれば体感速度は改善するのではないか」 |

問題解決の仮説だけを立てて走り出すと、問題の特定を飛ばすことになる。まず問題発見の仮説を検証し、そのうえで解決の仮説を立てる順番を守りたい。

### 仮説の立て方

「仮説を立てろと言われても出てこない」という声に対して、本書は視点を動かす方法を挙げている。

| 方法 | 内容 | エンジニアの例 |
|:---|:---|:---|
| 反対側から見る | 顧客、現場、競合など自分と違う立場で考える | 「利用者はこの画面をどの順で操作しているか」を想像する |
| 両極端に振る | 極端なケースを想定して本質を探る | 「利用者が10倍になったら」「1人だったら」どこが壊れるか |
| ゼロベースで考える | 今の制約を一度外して考える | 「この機能を今日ゼロから作るならどう設計するか」 |

インタビューや雑談、簡単な集計から拾う方法も本書では扱われている。共通するのは、**机上で完璧な仮説を練るのではなく、粗くても早く言葉にする**姿勢である。

### 良い仮説の条件

良い仮説とは、具体的なアクションに結びつくところまで掘り下げられた仮説である。

| 掘り下げが浅い仮説 | 掘り下げた仮説 |
|:---|:---|
| 「パフォーマンスが悪い」 | 「一覧APIのN+1クエリが原因で、表示件数に比例して遅くなっている」 |
| 「テストが不安定」 | 「テスト間で共有しているDBの状態が、並列実行時に競合している」 |
| 「オンボーディングに時間がかかる」 | 「ローカル環境構築の手順書が古く、最初の2日がそこで消えている」 |

左は現象の言い換えに過ぎず、次に何をすればよいか分からない。右は「一覧APIのクエリログを見る」「テストを直列で回して差を見る」「新メンバーの初週の時間の使い方を聞く」と、検証の手が自然に決まる。

### 検証はクイック＆ダーティで

仮説を立てたら、証明ではなく**確認**をする。本書は検証の手段として実験、ディスカッション、分析の3つを挙げ、いずれも「クイック＆ダーティ」、つまり粗くても速く回すことを勧めている。

- 全期間のログを集計する前に、直近1時間のサンプルだけ見る
- 全クエリを見る前に、最も遅い1リクエストだけEXPLAINを取る
- 資料を作る前に、隣の同僚に口頭で仮説をぶつける

最初の仮説が外れることは前提である。外れたら仮説を修正し、また検証する。このループを回すほど答えの精度が上がることを、本書は「仮説の進化」と呼んでいる。

```
仮説v1「DBが遅い」
  │ 検証：スロークエリログを見る → 該当なし
  ▼
仮説v2「外部APIの待ちが原因」
  │ 検証：APIごとの応答時間を見る → 決済APIだけ3秒超
  ▼
仮説v3「決済APIのタイムアウト設定が長すぎ、リトライも直列」
  │ 検証：設定値を確認 → タイムアウト30秒、リトライ3回
  ▼
問題解決の仮説へ 「タイムアウト短縮と非同期化で体感を改善できる」
```

### 空パッケージ：アウトプットの骨格を先に作る

本書で紹介される実践的な技法が「空パッケージ」である。調査を始める前に、最終アウトプットの目次や資料構成を空のまま先に作ってしまう。

設計ドキュメントで言えば、次のような骨格を最初に書く。

```markdown
# 一覧画面の表示速度改善

## 背景と論点
（なぜ今やるのか。何を解くと決めたのか）

## 現状の計測結果
（p50/p95の応答時間。ボトルネックの所在）

## 原因の仮説と検証結果
（仮説→検証→結論の順で）

## 対策案の比較
（2軸で整理する。後述）

## 採用案と実施計画

## リスクと未検証事項
```

見出しだけの状態で埋まらない箇所が、そのまま「これから調べるべきこと」になる。全部調べてから書き始めるのと比べて、調査の無駄が大きく減る。Pull Requestの説明文を実装前に書いてしまうのも、同じ発想である。

### デバッグを仮説駆動にする

仮説思考をいちばん体感しやすいのはデバッグである。調査ログを次の型で残すと、仮説と検証が自然に分かれる。

```markdown
## 現象
一覧画面の表示に5秒以上かかる（p95）。3日前から。

## 仮説1：3日前のデプロイで追加したクエリが重い
- 検証：デプロイ差分のSQLを確認 → 追加クエリなし
- 結論：棄却

## 仮説2：外部APIの応答が遅くなった
- 検証：APIごとの応答時間を直近1時間分だけ確認 → 決済APIがp95で3.2秒
- 結論：支持。次はタイムアウト設定を確認する

## 次の仮説
決済APIのタイムアウトとリトライ設定が、待ち時間を増幅している
```

「ログを全部読む」ではなく、「仮説2を確かめるために決済APIの応答時間だけ見る」と範囲が決まる。棄却した仮説も残しておくと、同僚が同じ道を辿らずに済む。

### 仮説思考力を高める：本書第5章より

本書の第5章は、仮説思考を日常で鍛える方法を扱っている。デバッグ以外の場面にも広げるための実践に翻訳する。

| 本書の指摘 | エンジニアの実践 |
|:---|:---|
| 「So What?」（だから何が言えるか）を繰り返す | 計測結果やログを見たら「だから何が言えるか」を1文で書く。数字を並べて終わりにしない |
| 「なぜ」を繰り返して掘り下げる | 障害の原因を「設定ミス」で止めず、「なぜその設定が入ったか」「なぜレビューで気づけなかったか」まで辿る |
| 日常の出来事で仮説を立てる訓練をする | 「このサービスはなぜこの料金体系なのか」のような身近な題材で仮説を立て、後で調べて答え合わせする |
| 失敗を恐れず仮説を口に出す | 外れることを前提に、レビューや朝会で「たぶんこうだと思う」と先に言う |

「So What?」と「なぜ」は対になっている。「なぜ」は原因へ遡る問いで、「So What?」は結果から先の含意を引き出す問いである。障害の原因を「なぜ」で掘り、そこから「だから次は何が起きるか、何をすべきか」を「So What?」で引き出すと、原因と対策が1本のストーリーになる。

本書は、仮説が外れても修正して前に進む粘り強さを重視している。仮説を口に出す回数が増えるほど修正の回数も増え、結果として精度が上がる。

## 実践編：整理するときは軸を2つまでにする

**ここからは書籍の解説ではなく、2冊の内容を実務に落とすときの筆者の実践ルールである。** 前章の動画を見て、自分の資料が軸を増やしすぎていると気づいたことがきっかけだった。

### なぜ3軸以上は伝わらないのか

- **2軸は1枚に収まる**。縦と横の表、あるいは4象限のマトリクスで表せる。3軸は立体になり、読む側が頭の中で図を回転させなければならない
- **軸が多いのは、論点が絞れていないサイン**である。どの軸で判断するか決めきれないから全部載せる。これは論点思考の失敗を比較表に持ち込んでいる状態と言える
- **読む側の負担が増える**。列が6つある比較表は、1列ずつ読んで頭の中で合成する作業を読者に強いる。判断を助けるはずの表が、判断を遅らせる

### 悪い例と良い例：技術選定の比較表

ライブラリ選定で、次のような表を作ったことはないだろうか。

| 候補 | 学習コスト | 性能 | エコシステム | 採用市場 | ライセンス | 運用負荷 |
|:---|:---|:---|:---|:---|:---|:---|
| A | 低 | 中 | 大 | 多 | MIT | 中 |
| B | 中 | 高 | 中 | 中 | Apache-2.0 | 低 |
| C | 高 | 高 | 小 | 少 | GPL | 高 |

情報は揃っているが、この表からは結論が読めない。6軸のうちどれを重く見るかが書かれていないからである。

論点を「半年以内に今のチームで安定運用に乗せられるか」と決めると、主軸は「チームの習熟度」と「運用負荷」の2つに絞られる。残りは軸ではなく**足切り条件**として先に処理する。

**足切り条件（Yes/Noで先に判定する）**

- ライセンスが商用利用可能か：Cは要件に合わないため除外
- 性能要件（p95で200ms以内）を満たすか：A、Bともに満たす
- エコシステムと採用市場が一定規模以上か：A、Bは満たす。Cは規模が小さく、この条件でも除外される

これで6つの観点は、主軸2つ（学習コストは「チームの習熟度」として、運用負荷はそのまま）と足切り条件4つ（ライセンス、性能、エコシステム、採用市場）に振り分けられた。捨てた観点はない。

**主軸で比較する（残ったA、Bのみ）**

| | 習熟度：低 | 習熟度：高 |
|:---|:---:|:---:|
| **運用負荷：低** | B | |
| **運用負荷：高** | | A |

この形にすると、「Bは運用が楽だが学習が必要、Aは今すぐ書けるが運用に手がかかる。半年という期限を考えると、まずAで立ち上げて運用負荷が見えたらBを再検討する」という判断の文章が書ける。6軸の表からは、この文章は出てこない。

### 2軸の選び方

1. 比較や整理に使いたい軸の候補を、いったん全部書き出す
2. 決めた論点に直結する順に並べ替える
3. 上位2つを軸にする
4. 残りは「足切り条件」にするか、2軸で絞ったあとの「第2段階の比較」に回す

手順1で軸を捨てないのがポイントである。捨てるのではなく、軸から条件へ役割を変える。こうすれば「その観点は見ていないのか」という指摘にも「足切りで確認済み」と答えられる。

### 例：バグのトリアージ

軸を「影響範囲」と「再現頻度」の2つに絞ると、対応順は4象限で決まる。

| | 影響：小（一部の利用者） | 影響：大（全利用者） |
|:---|:---|:---|
| **再現頻度：高** | 次スプリントで対応 | 今すぐ対応 |
| **再現頻度：低** | バックログへ | 再現条件を先に特定 |

「重大度」「発生日時」「報告者の役職」「修正の難しさ」も情報としては有用だが、対応順を決める軸には入れない。修正の難しさは、順番を決めたあとの見積もりの段階で使えばよい。

### よくある落とし穴

| 落とし穴 | 何が起きるか | 対処 |
|:---|:---|:---|
| 2軸が独立していない | 「開発工数」と「リリースまでの期間」、「工数」と「難易度」のように相関する軸を選ぶと、点が対角線上に並ぶだけで判断材料にならない | 一方を落として別の軸に替える |
| 足切り条件を軸にしてしまう | 「ライセンスがOKか」のようなYes/Noの項目を軸にすると、片側に全部寄って情報量がない | 条件は先に処理し、軸には連続的に差が出るものを選ぶ |
| 軸の目盛りが曖昧 | 「高/低」の基準が人によって違い、議論がずれる | 「高＝p95で1秒超」のように、目盛りの定義を1行で書く |

## 新任チームリーダーの1週間に当てはめる

リーダーになると、自分で解く時間よりメンバーに問いを渡す時間が増える。2冊の内容と2軸のルールを、典型的な場面に当てはめる。

| 場面 | 論点思考 | 仮説思考 | 2軸で整理 |
|:---|:---|:---|:---|
| スプリント計画 | 今スプリントの大論点を1文で書く | 各タスクに「終わったら何が変わるか」の仮説を添える | 優先順位は「価値」と「工数」の2軸で並べる |
| 1on1 | メンバーが抱える問題の中から、今解くべき論点を一緒に決める | 「たぶんこうでは」と仮の答えを口に出してもらう | 相談内容は「緊急度」と「本人の裁量で動けるか」で分ける |
| 障害対応 | 復旧と原因究明のどちらを今の論点にするか宣言する | 原因の仮説を時系列で残す | 対応順は「影響範囲」と「再現頻度」 |
| 上司への報告 | 上司の論点（何を知りたいか）を先に確認する | 結論を先に置き、根拠は検証結果で示す | 選択肢の比較は2軸のマトリクス1枚 |
| 技術選定 | 「何のために選ぶのか」を論点として確定する | 有力候補を仮説として先に置き、検証で確かめる | 主軸2つと足切り条件に分ける |

### メンバーへの問いかけを3つに絞る

メンバーが行き詰まっているとき、答えを教える前に投げる問いは3つで足りる。

1. 「今、解こうとしている論点は何か」
2. 「その仮説は何か」
3. 「どうやって検証するか」

1で論点がずれていれば手を動かす前に直せる。2で仮説が出てこなければ、視点を動かす方法（反対側から見る、両極端に振る、ゼロベース）を一緒に試す。3が「全部調べます」なら、クイック＆ダーティな確認方法を一緒に考える。

### やりがちな失敗

- **論点を決めずに手を動かす**。忙しいときほど起きる。5分だけ論点を書く時間を取るほうが結果的に速い
- **仮説を正解だと思い込む**。仮説は修正される前提のもの。検証で外れたら喜んで捨てる
- **すべての軸で比較表を作る**。丁寧に見えて、判断を読者に丸投げしている

## 明日から使うテンプレート

Issueや設計ドキュメントの冒頭に、次の4項目を置く。

```markdown
## 論点
（何を解くと決めたか。1文で）

## 仮説
（たぶん答えはこれ。アクションが決まる粒度まで掘り下げる）

## 検証方法
（何を見れば仮説の正誤が分かるか。最小の確認手段）

## 整理の軸（2つまで）
（比較や優先順位づけに使う軸。残りは足切り条件へ）
```

4項目が埋まらないなら、まだ手を動かす段階ではない。埋めるために人に聞く、仮の論点を提示して反応を見る、直近1時間のログだけ見る。それ自体が論点思考と仮説思考の実践になる。

## まとめ

- 2冊の章構成を地図として持っておく。『論点思考』は問いを選ぶ6章、『仮説思考』は答えに向かう7章で、実務ではこの順に使う
- **論点は自分で決める。** 依頼者の言葉は症状か解決策であることが多い。なぜ欲しいのかを辿り、解けるか、効果があるか、実行できるかの3条件で筋の良い論点を選ぶ
- **仮の答えを先に置く。** クイック＆ダーティに検証して進化させる。調べる前に空パッケージを作れば、埋まらない箇所が調べるべきことになる
- **整理は軸を2つまで。** 残りの観点は捨てるのではなく、足切り条件か第2段階へ役割を変える

原著はどちらも250ページ前後で、事例はコンサルティングの現場が中心である。本記事の翻訳表を手元に置いて読むと、自分の仕事への置き換えがしやすくなるはずである。
